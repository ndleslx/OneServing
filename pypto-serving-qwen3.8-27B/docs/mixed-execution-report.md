# Qwen3.8-27B PD 混合执行实现与性能验证

Qwen3.8-27B 的 TP1 执行路径已支持多个 prefill、decode 请求合批，通过统一计算图完成公共计算，并独立维护各请求的上下文和持久状态。在本文 HTTP 负载、相同活动请求上限下，**服务吞吐提升 40.3%～93.1%，TPOT P95 降低 34.7%～48.5%**。以下对比逐请求基线、MLP 合批方案和全程连续布局方案的实现及验证结果。

## 1. 基线：按请求执行完整模型

原方案已有连续调度和分块 prefill，同一轮可以选中处于不同阶段的请求。Runtime 根据本轮是否包含 prefill 选择入口，两个入口均按请求调用完整的 64 层计算：每个请求独立完成 Norm、Attention、MLP 和输出头，公共稠密计算尚未跨请求合批。

每个请求使用固定 16 行输入，prefill 最多填入 16 个有效 token，decode 填入 1 个有效 token。模型编译容量为 8，原服务活动请求上限为 2。

## 2. 混合执行方案

### 第一版：逐层合并 MLP

模型按层推进：每层分别执行各请求的 Norm 和 Attention，随后按有效 token 收拢数据，统一执行 MLP，再将结果写回请求槽位。MLP 使用 32 行计算块，尾部按块补齐。

Attention 输入/输出投影和最终输出头按请求执行，层间数据保留请求槽位布局。该图在 P/D 同时出现的批次启用，纯 prefill、纯 decode 使用基线图。

### 第二版：公共计算全程使用连续 token 布局（当前实现）

各请求的有效 token 从 embedding 到输出头始终采用连续布局。Norm、Attention 输入/输出投影、MLP 和输出头按 token 合批执行，计算块为 32 行；纯 prefill、纯 decode 和混合批次均使用该图。

Attention 核按请求片段访问上下文和状态，将结果直接写入连续缓冲区，消除每层 MLP 前后的布局转换。`packed_offsets` 定义 token 分段，`state_slots` 映射批次请求与持久状态槽位，保持请求重排、退出和槽位复用时的状态归属。

卷积和递归更新直接操作常驻状态视图，KV 按请求页表访问，移除混合路径中的状态压紧搬运。公共工作缓冲区跨层复用，尾部 padding 每轮初始化一次，请求局部缓冲通过 PyPTO 的 scope 回收。

实现入口：[模型图](../serving/model.py)、[Runtime](../serving/runtime.py)、[批次元数据](../serving/mixed_batch.py)。

## 3. 测试方法

测试使用 Ascend 910B3、同一份 Qwen3.8-27B checkpoint，拓扑为 TP1/DP1，保持原有精度、16-token prefill chunk 和编译容量 8。

- **模型对照**：三个方案使用相同请求组成、活动请求数和初始状态。P 每轮处理 16 个输入 token，D 每轮处理 1 个 token。每组交错运行三轮，每轮预热 2 步、测量 6 步，取三轮平均步耗时的中位数。计时包含 host 准备和输出读取，排除编译、权重加载及请求接纳。
- **HTTP 对照**：基线图、连续布局图分别配置 `max_active=2/8`，构成四组配置。同上限对照固定调度器和请求 trace，仅切换执行图；记录各批次的实际 active count、P/D 组成及请求进度。每组完整预热一次，再交错测四轮，各配置在每个执行位置各出现一次。
- **HTTP 负载**：8 个请求同时到达，输入长度为 1、1、1、17、65、129、193、257，每请求输出 16 token，greedy，关闭 prefix 命中。计时包含调度、状态初始化、输入准备和输出处理，排除编译、加载与预热。吞吐取四轮 token/s 的中位数，延迟分位数按每组 32 个请求计算。

模型吞吐提升按“基线步耗时 ÷ 对应方案步耗时 − 1”计算。HTTP 的吞吐和延迟均比较相同活动请求上限下的逐请求基线与连续布局方案。

## 6. 结果分析

**有效行利用率。** 1P+7D 包含 23 个有效 token，基线按请求补齐至 128 行，合批后仅需一个 32 行块。MLP 合批方案吞吐提升 42.2%；连续布局方案将合批范围扩展至其他公共计算，整轮吞吐提升 104.8%。

**计算分块与任务组织。** 8P 的 128 行全部有效，基线使用 8 个 16 行块，连续布局使用 4 个 32 行块，实测吞吐提升 41.6%。7P+1D 有 113 个有效 token，两种布局均补齐至 128 行，吞吐提升 41.8%。这两组负载的行容量保持一致，收益伴随计算分块、任务组织及公共计算执行方式的调整。

**执行覆盖范围。** MLP 合批方案在纯阶段批次使用基线图，连续布局方案在所有阶段组合中执行公共计算合批。8D 吞吐提升 107.3%，表明合批收益覆盖混合批次结束后的纯 decode 阶段。

上述结果衡量完整方案，包含层间连续布局、状态视图直接更新和尾部清零调整。各项改动的独立贡献及实际权重访存量未做单独测量。

## 7. 正确性验证与复验记录

6 项 CPU 元数据测试、1 项编译测试、5 项完整 64 层 NPU 测试通过。NPU 以逐请求基线为参考，比较生成 token、logits、有效 KV、卷积及递归状态，覆盖不同长度和历史位置、6～8 请求混合与重排、连续调度、槽位复用和 prefix 恢复。正确性测试在每次模型执行前将输出缓冲区置为 NaN，以检测输出未写入的情况。

模型性能测试的三个执行路径均通过有效 logits 有限性和最终 token 一致性检查。同上限 HTTP 对照四组各完成 32 个测量请求，共 **128 个、0 失败**，另有 32 个完整 trace 预热请求。所有请求均生成约定的 16 个 token，四种配置全部轮次的逐请求 token 一致，并与归档基线输出一致。

原始记录经独立重算，吞吐中位数、延迟分位数和排队时间与汇总数据一致；各轮 active count 均未超过配置上限，有效 token 处理总量一致。性能测量与 NPU 正确性验证使用的模型代码摘要一致，服务端源码与被测源码摘要已核对。

服务器 checkpoint 缺少 revision 元数据，验证时核对了部署契约中的三个文件摘要，各方案共用同一份权重，生产 loader 保持原检查。
